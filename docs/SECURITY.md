# Security design

This simulation assumes hostile clients and merchant endpoints. It does not provide regulatory compliance, real money custody, fraud detection, or identity proofing. Controls below are implementation requirements until tests demonstrate them.

Use Spring Security resource-server JWT validation with asymmetric signing, pinned algorithm, issuer, audience, exp/nbf validation and short clock skew. Access tokens expire in 10 minutes and carry subject/session ID, not authoritative mutable roles. Membership and enabled status are checked from PostgreSQL per request. Signing private keys come from a secret store; rotation uses kid and overlapping public verification keys. No committed keys or random restart-generated signing keys in normal operation.

Passwords use Argon2id via Spring PasswordEncoder with explicit tuned parameters and per-password salts. Limit length before hashing, return indistinguishable login failures, rate-limit IP/account, and rehash on successful login when parameters change. Refresh tokens are random 256-bit secrets, hashed in PostgreSQL, rotated once per use, expire in 7 days; reuse revokes the family. HttpOnly Secure SameSite cookie is narrowly scoped. Refresh/logout need CSRF token and origin checks. Stateless bearer financial APIs do not use ambient cookies and can disable CSRF on that chain only. Access tokens stay in frontend memory; no localStorage token persistence.

API keys contain 256 random bits. Store SHA-256 hash of the high-entropy secret and a public prefix for lookup; constant-time comparison, scopes, revocation, created/last-used timestamps, and transactionally audited issuance. Password hashing and random-token hashing have different threat models. Secret appears only in the creation response, never in lists, audit, traces, URLs or request logs. TLS protects transit. Revocation consults PostgreSQL; no long-lived positive cache initially.

Tenant isolation uses server-derived merchant IDs, membership checks, resource predicates and composite FKs. A UUID is not a capability. Tests must try every resource route as another merchant and VIEWER, including response replay, nested refund IDs, ledger joins, exports, webhook replay, and pagination. RLS is deferred until connection-pool context/reset semantics are implemented and tested; do not claim it exists.

Webhook secrets must be recoverable for signing, so use AES-GCM encryption with an external versioned key and unique nonce rather than hashing. Sign exact bytes as HMAC-SHA256(secret, timestamp + '.' + rawBody). Headers carry delivery/event ID, timestamp, and v1 signature. Receiver checks constant-time signature, timestamp within five minutes, and persistent event-ID deduplication. New timestamp/signature for each attempt; stable event ID across replay.

SSRF: HTTPS only, no URL userinfo/fragments, bounded URL length, allow port 443 initially, deny loopback/private/link-local/multicast/metadata destinations, validate every DNS answer, disable redirects, cap response bytes and deadlines. Registration-time checks alone do not stop DNS rebinding: worker must connect to vetted addresses with hostname/SNI verification or use a enforcing egress proxy. Production network policy denies internal/metadata ranges as defense in depth. A local receiver requires an explicit demo-only allowlist, never a blanket production bypass.

Use parameterized SQL, DTO validation, escaped React text, no unsafe HTML rendering, CSP/security headers, narrow CORS allowlist, no credentialed wildcard origin, request/body size limits and sanitized errors. Log only structured safe fields; do not log bodies, headers, password hashes, JWTs, API keys, raw webhook response PII, or arbitrary metadata. Audit events record actor/action/IDs and sanitized reason codes.

Redis rate limit key `lf:rl:v1:<dimension>:<hashed-id>:<window>` with 60s windows and 120s expiry. Atomic Lua increments + expiry; default limits configurable. Return 429, Retry-After and remaining/reset headers. Redis failure fails closed (503) for public credential endpoints and mutation APIs; financial integrity remains protected by PostgreSQL. Authenticated reads can fail open with a metric and gateway cap. This is an explicit availability tradeoff, not a correctness dependency.

Separate migration/runtime database roles; runtime cannot alter schema or delete ledger/audit history. Restrict Actuator and broker access to internal networks. Dependencies are pinned and reviewed/scanned in CI; patch updates need tests. Backup restore, signing/encryption-key custody, deployment TLS and egress enforcement are operator responsibilities. No production readiness claim until these are exercised.
