# Redis and rate limits

Redis 8.10.2 is a disposable abuse-control store. PostgreSQL remains authoritative for money, idempotency and jobs. Spring Data Redis/Lettuce versions come from the Spring Boot BOM and are recorded in the dependency lockfile.

An atomic single-key Lua operation increments a bounded counter and sets its expiry together. Keys are `lf:rate:v1:<dimension>:<SHA256(identity)>`, with a 60-second TTL from the first request. Dimensions are auth-ip (30 requests/window), ip (600), and authenticated principal (300). Principals use verified JWT subjects or verified API-key IDs, never a user-supplied merchant header or secret. Different application replicas share these counters. They expire naturally; no invalidation job or financial cache exists. Fixed windows permit a burst across expiry boundaries and are intentionally simpler than a sliding-window algorithm.

The early IP filter protects authentication/database work. A second Spring Security filter runs after bearer authentication. HTTP 429 includes Retry-After, X-RateLimit-Limit, X-RateLimit-Remaining and RFC 9457-style JSON. The last applicable limit supplies the normal-response headers. Counters cap at limit+1, avoiding unbounded increments under sustained rejection. Idempotent retries still consume rate budget.

Redis timeouts are 300 ms. A failure opens a process-local one-second retry suppression window; requests receive 503 before executing financial commands. Readiness/liveness do not depend on Redis, avoiding restart storms. There is no automatic financial retry. Retry the unchanged command with the original idempotency key after recovery. A Redis restart/eviction resets abuse budgets and can allow another window of requests; it cannot duplicate a ledger transaction or bypass PostgreSQL idempotency. Configure a private authenticated/TLS Redis endpoint and memory/eviction policy in production.

IP identity is the actual socket peer. Forwarded headers are not trusted, so clients cannot spoof a bypass. Behind a shared Nginx/Ingress proxy this deliberately gives a coarse shared IP budget; deploy a trusted edge limiter and configure a reviewed proxy-address policy before broad public exposure. Per-user/API-key limits remain separate. There is no account/email-specific lockout, CAPTCHA or distributed DDoS protection.

RATE_LIMIT_ENABLED defaults true. Start Redis with the events infrastructure profile. Only trusted host development may set it false; the Helm chart enables it. Tests unrelated to Redis disable the limiter explicitly, while dedicated Testcontainers tests use real Redis to verify concurrent admission, TTL reset, HTTP headers, verified identity isolation, timeout and recovery. Lua follows the [Redis atomic counter guidance](https://redis.io/docs/latest/commands/incr/).
